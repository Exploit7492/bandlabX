# 2.b.i.zi — Record the bundle evidence and the spec's server block

**Leaf:** 9 of 73 (`2.b.i.zi`). Originally the owner's leaf; resolved from public sources.
**Date:** 2026-10-15.

## Why this leaf changed hands

The leaf was `BLOCKED_ON_OWNER`: it needed the owner to hand back scrubbed HAR captures, and every
Phase 3 leaf waited behind it. This session found that the evidence was publicly available all
along, in two places:

1. the OpenAPI spec URL already recorded in `.stats.yml`, and
2. BandLab's own shipped web app bundle.

No capture from the owner was required to answer the question the leaf was asking.

## What was done

1. **Fetched the OpenAPI spec** from the `openapi_spec_url` in `.stats.yml`. It resolves: 6,752
   lines, 55 paths, 123 operations. Its `servers:` block names both hosts, which **answers P0**.
2. **Fetched the web app bundle** `web-app/scripts/CYjIzzub.js` (1,947,947 bytes) and all **217
   lazy-loaded chunks** it imports.
3. **Extracted every API path** by regex over the bundle and chunks, normalising template
   parameters to `{p}` and discarding malformed matches. 236 raw templates → **225 clean paths**
   across 4 API versions.
4. **Diffed against the SDK's 123 endpoints.** 24 overlap; **201 are not in the SDK**.
5. **Probed a representative sample of 53 endpoints live** against `test.bandlab.com`. 26 returned
   a non-404 status, confirming the route exists; 24 returned 404; 2 returned 500; 1 returned 204.
6. **Grouped the 201 new endpoints into 24 domains** and mapped each to a proposed resource file
   and a Phase 3 leaf.

## The decisive finding

The spec is **not** a superset of BandLab's API. It is a narrow subset:

| Set                | Path templates | Operations                      |
| ------------------ | -------------- | ------------------------------- |
| OpenAPI spec / SDK | 80             | 123                             |
| Web app bundle     | 225 clean      | 145 method+path pairs recovered |
| Union              | —              | **201 new** + 123 existing      |

The spec contains **no** messaging, effects, sounds or uploads. Those capabilities exist in the
product and in the app bundle but were never in the generated spec. `COVERAGE.md` had therefore
been searching for evidence in a document that does not describe them — which is exactly why
Phase 3 could not start.

## The 404 trap (recorded because it invalidates a tempting shortcut)

An earlier session tried to discover endpoints by fabricating candidate paths and probing them.
**This cannot work.** Endpoints known to be real and present in the spec — `/badges`, `/validation`,
`/reports`, `/bands/{id}` — also return 404 unauthenticated. 404 carries no information here. So
"probe and keep whatever is not 404" would keep fabricated endpoints and discard real ones. This
is now rule D13 in `HANDOVER.md` Section 2.

## What is still NOT evidenced

Stated plainly so no later session overclaims:

- **Request/response shapes for the 201 new endpoints.** Source maps are 404
  (`CYjIzzub.js.map` and per-chunk `.map`), so the bundle yields paths, not types.
- **Verbs for ~80 path-only endpoints.** 145 method+path pairs were recovered; the rest are
  path-only. REST convention must not be assumed to fill the gap — `POST /songs` returned 404
  while `GET /songs/{id}/invite-link` returned 403.
- **Behaviour of the `v2.0` uploads, `v3.0` sounds and `v4.3` soundbanks routes.** They do not
  resolve from the web host at all; they are mobile/studio-client routes.
- **`POST /songs` specifically** — returned 404, so the create-song verb is unconfirmed.
