## What was implemented

- `songs.forks(body, options)` → `Song` (`POST /songs/forks`). Body is `unknown`: the app's body
  model `vrb` is obfuscated, so rule D12 forbids naming fields.
- `songs.retrieveInviteLink(songID)` → `InviteLink` (`GET /songs/{id}/invite-link`).
- `songs.invites.listInvites` now returns `InviteListResponse` (typed from
  `com.bandlab.invite.api.Invite`), and `songs.invites.sendInvites` keeps `void`.
- New types: `InviteLink`, `Invite`, `InviteListResponse`. Paging reuses the existing
  `users/followers` `Paging` type instead of a new one.

## Bug found and fixed: the singular `/song/...` route

The SDK called `GET /song/{songId}/posts`, `GET /song/{songId}/invites` and
`POST /song/{songId}/invites`. Every evidence source says the plural `/songs/...`:

1. **APK**: `RemoteSongService.getRevisionPosts` is annotated `@xbc("songs/{id}/posts")`;
   `InviteService.getSongInvites` is `@xbc("songs/{id}/invites?accepted=false")`;
   `InviteToSongService.sendInvite` is `@kik("songs/{id}/invites")`.
2. **Live route probe** (unauthenticated, rule D13):

   | Request | Result | Reading |
   |---|---|---|
   | `GET /song/{guid}/posts` | 404 `Unable to find the page you're looking for` | route absent |
   | `GET /songs/{guid}/posts` | 404 `Couldn't find any matching element, it might be deleted` | route present |
   | `GET /song/{guid}/invite-link` | 404 page-not-found | route absent |
   | `GET /songs/{guid}/invite-link` | 403 permission | route present |
   | `GET /songs/{guid}/posts` | 400 `The value '...' is not valid for SongId` | route present, model-bound |

   The two 404s differ: the framework page is returned when no route matches, the
   `errorCode:0` body when the route matches and the resource is missing. The model-binding
   400 names the parameter (`SongId`, `Guid`), which only happens after routing succeeds.

`/song/.../invites` answers 401 for both spellings, so it does not discriminate; the APK decides
there, and both the app and every other `songs` method use the plural.

This is a real defect in the shipped client: those three calls hit a non-existent route. The fix
keeps the method names, so rule D4 (additive only) holds — only the URL changed, to the one the
app actually uses.
